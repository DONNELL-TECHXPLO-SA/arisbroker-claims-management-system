# 2026-09-17 — BRD v0.7 Adopted as Requirements Baseline

## Context

TechXplo delivered "Claims Management Portal BRD v0.7" (dated 17 Sep 2026) to Aris Brokers as a
"Draft – for client review". The document is the result of two requirements-gathering sessions plus a
report-template review cycle (v0.1 → v0.7, 19 Aug – 17 Sep 2026), and was independently reviewed by Donnell
Naidoo (Lead Software Developer, TechXplo) prior to issue.

This decision record captures that the BRD has been **fully analysed and organised** into this project's
existing documentation structure (Phase 1 of the current engagement — requirements organisation, not
architecture). It does not itself constitute the Client's formal sign-off, which remains a separate step.

## Options Considered

1. Wait for the Client's formal sign-off before organising the BRD into the project docs.
2. Organise the BRD into the existing docs structure now, on the understanding that it is a "Draft – for
   client review" baseline, so that architecture/design work can begin promptly once sign-off is received
   and so that open items are visible to all parties in the meantime.

**Decision: Option 2.** The BRD is treated as the current source of truth for requirements, organised into
the existing folder structure, with every item the BRD itself flags as unresolved carried forward
transparently into [`../../02-requirements/open-questions.md`](../../02-requirements/open-questions.md)
rather than being assumed away.

## Decision

- BRD v0.7 is adopted as the requirements baseline across [`../../01-overview/`](../../01-overview/),
  [`../../02-requirements/`](../../02-requirements/), [`../../07-testing/test-cases.md`](../../07-testing/test-cases.md),
  and [`risk-register.md`](../risk-register.md)-adjacent files in this folder.
- Formal acceptance of scope and authorisation to proceed with build is recorded via the accompanying
  Scope of Work document, signed separately by Aris Brokers (per BRD Section 19, Document Sign-Off) — this
  has **not yet occurred** as at this record's date.
- No technical architecture, database, or API design decisions have been made as part of this baseline —
  those remain deliberately deferred to a subsequent phase (see
  [`../../03-architecture/README.md`](../../03-architecture/README.md) and
  [`../../04-design/README.md`](../../04-design/README.md), both still unpopulated).

## What's Resolved vs. Still Open

- **33 Functional Requirements** (FR-01–FR-33), **12 Non-Functional Requirements** (NFR-01–NFR-12), **15
  Use Cases**, **15 Test Cases**, **5 user roles**, a full data dictionary, and document requirements for
  **28 of 29** confirmed products are captured and cross-referenced (see
  [`../../02-requirements/traceability-matrix.md`](../../02-requirements/traceability-matrix.md)).
- **17 open items** remain unresolved and require Client/joint input before they can be finalised — see
  [`../../02-requirements/open-questions.md`](../../02-requirements/open-questions.md) for the full list
  (covering product-specific workflows, the Credit Insurance document list, hosting/SLA targets, and
  several report-content details).
- **8 project risks** are logged as Open — see [`../risk-register.md`](../risk-register.md).

## Consequences

- Any future requirement raised outside the BRD should continue the existing ID sequences
  (FR-34, NFR-13, Q-018 onward) rather than restarting numbering, per the convention noted in
  [`../../02-requirements/functional-requirements.md`](../../02-requirements/functional-requirements.md).
- Once the Client's formal BRD/SOW sign-off is received, this record should be updated (or a follow-up
  decision record added) noting the sign-off date, and the project can proceed to Phase 2 (technical
  architecture, database, and API design), informed by — but not constrained by — the structure of this
  requirements baseline.
